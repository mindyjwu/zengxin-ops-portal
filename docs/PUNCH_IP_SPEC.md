# 打卡 IP 位置：後端規格草案（IT 用）

依 10/20 會議：記錄網路位置（IP）、不強制拍照、位置只給後台看、手機介面不顯示、出勤紀錄保存五年、離線先暫存、連網自動上傳。
參考實作與測試：`backend/punch-ip.js`、`__tests__/punch-ip.test.js`。

## 1. 流程
1. 手機按「打卡」→ 送出 `{empId, type(in/out), clientTime, offlineQueued}` 到後端（不送定位、不強制照片）。
2. 後端在收到請求時自己讀取來源 IP（`clientIp`），不由手機回報，所以員工不用授權定位。
3. 依辦公室網路清單標示（`classifyIp`）：office／other／unknown，連同 IP 存進打卡紀錄（`punchRecord`）。
4. 只有有權限的後台角色（權限 `punchLoc`）查得到 IP 與標示；手機 API 的回應不含這兩個欄位。

## 2. 要注意的技術點
- **X-Forwarded-For 不能直接取最左邊**：使用者可以自己加標頭偽造。要從右邊數，跳過信任的代理層數（`trustedHops`）；部署在 Google 的負載平衡器後面時，層數要照實際架構量測後設定。
- **離線打卡**：IP 是「上傳當下」的位置，不是按下打卡當下的位置。離線補傳的紀錄要標 `offlineQueued`，後台顯示「補傳」，不要把補傳時的 IP 當成打卡地點。時間用手機記下的時間，並與伺服器收到時間一起存，差距過大要提醒。
- **IP 不等於實際位置**：行動網路、VPN、家用寬頻都可能對不上。所以做法是比對「辦公室網路清單」，不是查 IP 的地理位置；外勤（居服員）本來就預期在辦公室網路之外，標示為 other 不代表異常。
- **IPv6**：參考實作目前只比對 IPv4（含 IPv4-mapped）；辦公室若是 IPv6 要補上。
- 地理位置資料庫（如離線 IP 資料庫）只在「想顯示大概縣市」時才需要，建議第一版不做。

## 3. 資料欄位（打卡紀錄）
`empId, type, at(伺服器收到時間), clientAt(手機時間), ip, netKind, netPlace, offlineQueued, keepUntil`
- `keepUntil`＝紀錄日期＋5 年（勞基法第 30 條：出勤紀錄保存五年、記錄到分鐘；違反罰 9–45 萬）。到期前不得刪除，到期後再依個資法銷毀。

## 4. 個資與告知（需要法遵確認）
IP 可能識別個人。建議：入職或啟用時告知員工蒐集目的（出勤佐證）、只在打卡時蒐集、保存期限、誰看得到。我沒有查到個資法對 IP／定位的具體條文，**這部分請法遵或律師確認**，不能只靠本文件。

## 5. 還需要 IT 決定
1. 辦公室網路清單：各據點對外固定 IP 或網段（誠馨、誠芯、牛津各館）。
2. 後端放在哪一層代理後面（決定 `trustedHops`）。
3. other／unknown 的打卡在後台怎麼提醒（只標示，還是要主管確認）。
4. 補傳紀錄的時間差門檻。

## 6. 10/28 補充：浮動 IP 與「鎖 WiFi 名稱」的技術限制（我的判斷，請 IT 驗證）
需求端說明：公司是浮動 IP、WiFi 名稱可抓取，想確認「鎖 IP（192.168.x.x 網段）」或「鎖 WiFi 名稱」哪種可行。
- **192.168.x.x 做不到**：那是辦公室內網位址。伺服器收到的是辦公室對外的**公網 IP**（經過路由器 NAT），看不到內網位址，所以不能用它判斷。
- **WiFi 名稱（SSID）網頁讀不到**：瀏覽器不開放；加到主畫面的 PWA 也一樣。只有原生 App 在取得系統權限後才可能（Android 需要定位權限，iOS 需要特殊權限），而且 SSID 可以被同名的熱點偽裝。
- **浮動公網 IP 會讓清單失效**。可行做法：①向電信申請固定 IP（費用未查證）；②動態網域（DDNS）：辦公室路由器定期更新網域名稱，系統定時解析取得目前 IP，再更新辦公室網段清單；③辦公室放 QR code，員工掃碼才算辦公室打卡。
- 因為規則是「只記錄、不強制」，不鎖也不影響打卡，只是 office／other 標示可能不準。外訪是榮譽制，104 目前顯示的打卡位置要請需求端確認。
- 員工打卡前需簽告知同意書；各類員工的打卡流程（辦公室、外訪）需求端整理後提供，用來決定要支援幾種模式。
