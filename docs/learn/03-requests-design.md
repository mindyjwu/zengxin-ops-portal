# 第 3 課：請假、加班、補打卡與簽核的資料庫設計（白話說明）

這是我替你設計的版本。重點不是「照著用」，而是看懂每個選擇的理由，之後你想改，知道會牽動什麼。

## 資料表總覽
```
employees ──┐ manager_id（直屬主管，簽核第一關）
            │
requests ───┼── leave_requests       請假明細（假別、起訖、時數）
 （申請單） ├── overtime_requests    加班明細（日期、時間、時數、換加班費或補休）
            ├── punch_fix_requests   補打卡明細
            └── approvals            簽核紀錄（只能新增）
leave_types / leave_groups           假別設定與合併上限（人資可改）
```

## 我做的 7 個設計選擇與理由
1. **三種申請共用一張 `requests`，各自的細節分表。**
   好處：「我的申請」「待我簽核」「簽核歷程」只要寫一套；壞處：查請假細節要多 join 一次。替代方案是三張完全獨立的表，簽核邏輯要寫三遍，很容易寫得不一致。
2. **狀態規則寫在資料庫的觸發器裡**（`requests_status_guard`）。
   就算有人繞過 API、直接改資料庫，也不能把「待主管」直接改成「已核准」，或把已核准退回待簽。API 當然也檢查，但資料庫是最後一道。
3. **簽核紀錄 `approvals` 只能新增**（觸發器擋掉 UPDATE 和 DELETE）。
   誰在什麼時間做了什麼、寫了什麼意見，永遠改不掉。這是稽核與勞資爭議時的證據。
4. **請假時間重疊用觸發器擋**，只計「進行中」的單（待簽、已核准）。
   被駁回、抽單的單不佔時間。想想：為什麼不用唯一索引？（因為「時間區間重疊」不是單一欄位相等的問題。正式做法是 PostgreSQL 的 `EXCLUDE USING gist`，需要 `btree_gist` 擴充；觸發器是比較容易在任何環境跑的替代。）
5. **時數用 `numeric(5,1)`，並用 CHECK 限制是 0.5 的倍數。** 不用浮點數，避免 0.1+0.2 這類誤差；金額之後也一樣用整數或 numeric。
6. **額度（每年幾小時、每月、每次事件、合併上限）放在資料表 `leave_types`，由程式計算餘額。**
   理由：人資能自己調整，不用改程式。代價：額度檢查在 API，不是資料庫約束。要補強就要在交易裡鎖住該員工的資料列（目前用「重疊」觸發器與 API 檢查，並發極端情況下仍可能超額，上線前要補壓力測試）。
7. **時間用 `timestamptz`（含時區），額度期間用台北時間切年與月。** 避免跨日、跨年請假被算到錯誤的一期。

## 簽核流程（沿用原型）
申請人送出 → 直屬主管核准（`pending`）→ 人資複核（`countersign`）→ 核准（`approved`）。
- 不能簽自己的單，就算你有簽核權限（有測試專門檢查）
- 駁回一定要寫理由；申請人可以在待簽階段抽單；核准後可銷假（申請人只能銷未來的，人資可銷任何一張）
- 補打卡核准後，伺服器自動把那筆打卡補進 `punches`，標示 `source='fix'`

2. 直接用 SQL 把一張已核准的單改成 `pending`，會看到什麼錯誤？為什麼這比只靠 API 更安全？
