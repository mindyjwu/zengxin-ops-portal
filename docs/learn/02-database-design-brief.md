## 你的作業：請假、加班、補打卡與簽核的資料表
目標：寫一個 migration 檔 `server/migrations/002_leave_ot_approvals.sql`，讓後端能存這些資料。測試會自動執行它（`server/db.js` 會照檔名順序跑）。

### 網站現在的資料長什麼樣（原型）
- **請假**：單號（L241）、員工、假別（19 種，如 annual、sick、bereave1…）、起訖日期與時間、**請假時數**（0.5 小時為單位）、申請日、狀態、事由、附件（診斷證明）
- **加班**：單號（OT31）、員工、日期、起訖時間、時數、換「加班費」或「補休」、申請日、狀態、事由
- **補打卡**：單號（F12）、員工、種類、日期、狀態
- **簽核狀態**：待主管簽核 → 待人資複核 → 已核准；也可能已駁回、已銷假、已抽單
- **簽核路徑**：依組織圖 V3 逐層往上簽（不同身分層級不同）；報價單、出差、零佣金三種表單流程相同

### 規則（資料庫要幫忙守住的）
1. 請假時數必須大於 0，且是 0.5 的倍數
2. 起日不能晚於迄日
3. 同一員工的請假時間不能重疊（進階：用 PostgreSQL 的 `EXCLUDE` 約束，或在應用程式檢查並說明理由）
4. 狀態只能是上面那幾種；已核准的不能直接改回待簽核（想想怎麼設計「狀態變更歷程」）
5. 加班只能是「換加班費」或「換補休」
6. 誰在什麼時間做了簽核動作、意見是什麼，都要留下來，之後不能被改寫
7. 假別的上限（每年幾小時、病假類合計 264、事假類合計 112）：想一想放在資料表還是程式裡，各有什麼好壞

### 設計時請自己回答這些問題
- 請假、加班、補打卡要分三張表，還是一張「申請單」表加類型？各自的好壞是什麼？
- 簽核要用「一張申請單一個狀態欄位」，還是另外一張「簽核步驟」表？如果組織圖改了，舊的簽核紀錄會怎樣？
- 假別 19 種、簽核層級，放資料表（可以由人資改）還是寫死在程式裡？
- 附件（診斷證明）存在哪裡？資料庫只存什麼？
- 時間用什麼型別？（提示：台北時間、跨日請假、`timestamptz` 與 `date` 的差別）
- 金額與時數用什麼型別？為什麼不能用浮點數存金額？
- 刪除怎麼處理？（實刪、軟刪，或根本不能刪）出勤相關紀錄法定要保存五年
- 要建哪些索引？哪些查詢會最常用？（某員工某個月的請假、主管的待簽核清單）

### 交件格式

- 一段說明（可以寫在 PR 描述）：你的設計選擇與取捨，列出最不確定的 3 個地方

### 我會怎麼審
| 項目 | 看什麼 |
|---|---|
| 正確性 | 規則是否真的由資料庫守住，而不只是寫在註解 |
| 完整性 | 外鍵、非空、檢查約束、唯一性是否齊全 |
| 演進 | 組織圖與假別改了，舊資料會不會壞；有沒有為第二版（薪資）留空間 |
| 查詢 | 最常用的查詢有沒有索引，會不會需要全表掃描 |
| 隱私與稽核 | 個資放哪裡、誰能看、紀錄能不能被偷偷改掉 |
| 取捨說明 | 你的理由站得住腳嗎（沒有唯一答案） |
