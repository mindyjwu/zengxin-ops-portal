# 第 1 課：這個專案的各個零件怎麼接在一起

目標：看完能用自己的話說出「按下打卡」到「資料存進資料庫」中間發生了什麼，以及每一步在哪裡可能出錯。

## 一次打卡的旅程
1. **手機（瀏覽器）**：員工按「上班打卡」，網頁送出 `POST /api/punch`，內容只有 `kind`（in/out）、手機記下的時間、是否離線補傳。**不送位置。**
2. **Cloud Run（server/app.js）**：收到請求，先經過幾道檢查：
   - 安全標頭與 Origin 檢查（擋別的網站偷偷送請求）
   - 讀 cookie → 驗簽章 → 查資料庫確認這位員工還在職（`server/auth.js`）
3. **伺服器自己讀 IP**（`backend/punch-ip.js`）：不信任手機傳的位置。注意 `X-Forwarded-For` 最左邊可以被偽造，所以從右邊數、跳過我們信任的代理層數。
4. **寫進資料庫**（`punches` 表）：伺服器收到的時間、手機時間、IP、辦公室或其他網路、保存到期日（五年）。
5. **寫稽核紀錄**（`audit_log`）：誰、做了什麼、從哪裡。
6. **回應手機**：只回 `id、at、kind`，**沒有 IP**。位置只有後台有權限的角色查得到，而且查一次就留一筆紀錄。

## 這個設計背後的觀念（對照你學過的 CS）
| 觀念 | 在這個專案哪裡 |
|---|---|
| 驗證（authentication）vs 授權（authorization） | Google 登入證明「你是誰」；`permissions.js` 決定「你能做什麼」 |
| 不信任客戶端 | 權限、時間、IP 都由伺服器決定，網頁畫面藏按鈕不算權限 |
| 最小權限 | 員工只能看自己；位置要 `punchLoc` 權限；稽核紀錄只有 `perms` 權限 |
| 簽章與 HMAC | session cookie 用 HMAC-SHA256 簽名，被改過就失效 |
| 不可否認與追溯 | `audit_log`，包含「拒絕」與「查看別人位置」 |
| 資料庫約束 | `CHECK (kind IN ('in','out'))`、外鍵：壞資料連資料庫都寫不進去 |
| Migration | `server/migrations/` 版本化建表，可重跑、可追蹤 |
| 測試替身 | Google 驗證在測試裡換成假的；資料庫用 PGlite |

## 練習（建議 30–45 分鐘）
1. 執行 `npm run test:unit`，打開 `__tests__/server.test.js`，找出哪個測試保護「位置不回傳給手機」。
2. 把 `server/app.js` 裡 `/api/punches` 的 `withLoc` 條件改成永遠 `true`，再跑測試：哪些測試會失敗？為什麼？（改完記得還原）
3. 想一想：如果辦公室公網 IP 每天變，`offices.cidrs` 會出什麼問題？有哪三種解法？（提示：看 `docs/PUNCH_IP_SPEC.md` 第 6 節）
4. 問工程師的問題：「session 被偷走怎麼辦？我們有哪些緩解？」（答案方向：HttpOnly、Secure、短效期、登出、異常登入稽核）
